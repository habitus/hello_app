## Concepts

### Repository (repo)

**What it is:** A repository is a project folder whose entire history is tracked by a tool called Git. Every saved change (called a "commit") is recorded with a note explaining what changed and why, so you can look back at any earlier version or undo a mistake.

**Analogy:** A repository works like a document with unlimited, labelled version history. Each commit is like pressing "save as new version" and writing a sentence about what you changed.

**Example:** This project lives in a repository called `habitus/hello_app` on GitHub. GitHub is a website that stores repositories online so they are backed up and can be shared.

**Why it matters:** Every piece of code, documentation and decision for the project lives in the repository. Starting in the right repository means starting on the right foundation.

*First discussed: 2026-09-30*

### Starting a fresh repository

**What it means:** Starting a fresh repository means creating a brand new, empty project on GitHub for the real idea, instead of building on top of an existing one. The old repository stays where it is and is left untouched.

**Analogy:** Renovating a very old house can cost more effort than building a new one on a clear plot, because the old wiring and plumbing were made for a different era. A fresh repository is the clear plot.

**Example:** `hello_app` was generated by a Rails tutorial around 2015. It uses Rails 4.2.2, a version that stopped receiving security fixes years ago, and it contains only a single "hello" page. Upgrading it would take more work than starting cleanly with current tools chosen for the actual idea.

**How to do it:**
1. Sign in to GitHub and choose **New repository** (the "+" menu in the top right corner).
2. Give it a short, descriptive name, choose Private or Public, and tick "Add a README file".
3. Connect it to a Claude Code session so Claude can read and write to it. Claude can also create the repository on your behalf if you give permission.

**Why it matters:** A production-grade project needs a supported, secure foundation. Choosing the tools after the idea is defined means the foundation fits the project.

*First discussed: 2026-09-30*

### .gitignore file

**What it is:** A `.gitignore` is a small text file in a repository that lists files and folders Git should never save or upload. It usually covers secrets (such as passwords and API keys), temporary files, and large folders of downloaded libraries that can be recreated at any time.

**Analogy:** A `.gitignore` is like a "do not pack" list for a house move. The removal team (Git) sees the list and leaves those items behind, so rubbish and valuables that should stay private never end up on the truck.

**Example:** A JavaScript project usually lists `node_modules/` (thousands of downloaded library files) and `.env` (a file holding secret keys) in its `.gitignore`. Anyone who copies the project can download the libraries again, and the secrets stay on the owner's machine.

**Why it matters:** Accidentally uploading a secret key to GitHub is one of the most common and costly beginner mistakes, because automated bots scan GitHub for leaked keys within minutes. The right `.gitignore` depends on the tech stack, so this project leaves the GitHub template set to "None" and adds a matching `.gitignore` once the stack is chosen.

*First discussed: 2026-09-30*

### Software license

**What it is:** A software license is a file in a repository that states what other people are allowed to do with the code, such as copying, changing, or selling it. When a repository has no license, the author keeps all rights by default and nobody else may legally reuse the code.

**Analogy:** A license is like the terms written on a recipe card you hand out. Without terms, the recipe is still yours and others may only look at it. With terms such as "free to cook and share, just credit me", you give others permission in advance.

**Example:** The MIT License is a common, simple open source license. It lets anyone use and change the code for any purpose, as long as they keep the original copyright notice.

**Why it matters:** For a private project, having no license is the right default because it keeps full control with the owner. If the project is later made public as open source, adding a license file takes one step.

*First discussed: 2026-09-30*

### Agent skills and the development lifecycle

**What it is:** An agent skill is a written set of instructions that tells an AI coding agent (such as Claude) how to carry out a specific kind of work to a professional standard. Addy Osmani, a former Google engineer who now works at Anthropic on Claude Code, published a collection of these at [github.com/addyosmani/agent-skills](https://github.com/addyosmani/agent-skills). His collection follows the six stages that experienced engineers move through when building software.

| Stage | Command | The question it answers |
|---|---|---|
| Define | `/spec` | What exactly are we building, and for whom? |
| Plan | `/plan` | What are the small steps, and in what order? |
| Build | `/build` | How do we make one small working piece at a time? |
| Verify | `/test` | How do we prove each piece works? |
| Review | `/review` | What did we miss in quality or security? |
| Ship | `/ship` | How do we release it safely and keep it running? |

**Analogy:** The lifecycle is like building a house. You agree the design with the client (Define), draw up the build schedule (Plan), build room by room (Build), have each room inspected (Verify), do a final walkthrough (Review), and then hand over the keys with a maintenance plan (Ship).

**Example:** Before writing any code for a new idea, the Define stage would produce a one-page spec such as "A booking app where yoga students can reserve a class spot and receive a reminder the day before."

**Why it matters:** Beginners often jump straight into code and skip the questions that prevent expensive rework later. Following the stages in order teaches the professional process as well as producing the product.

*First discussed: 2026-09-30*

### ADR (Architecture Decision Record)

**What it is:** An ADR is a short note, usually under a page, that records one significant technical decision and the reasoning behind it. It has four parts:

- **Context:** the problem or situation that forced a choice.
- **Decision:** what was chosen.
- **Alternatives:** the other options that were considered, and why they were rejected.
- **Consequences:** the trade-offs being accepted.

**Analogy:** An ADR is like the minutes of a meeting where one important choice was made. Anyone who joins later can read why the choice was made instead of guessing or reopening the debate.

**Example:** "We will use PostgreSQL as our database instead of MongoDB, because our data is made of related records (students, classes and bookings) and we need bookings to be saved reliably. The trade-off is that we must define the structure of our data up front."

**Why it matters:** Six months later, you, a collaborator or an AI agent can see why things were built a certain way. This prevents a good decision from being undone by accident. For a learner, a folder of ADRs also becomes a record of the reasoning learned along the way.

*First discussed: 2026-09-30*
